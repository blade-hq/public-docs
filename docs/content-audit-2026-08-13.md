## 1. 执行摘要

### 1.1 一句话结论

这个站点当前的问题不是"设计不够好看"，而是**三个栏目共用同一套营销模板、内容密度远低于版式规格，并且已经出现了可验证的事实错误和死链**。用户提出的四条意见我全部认同，而且实际情况比用户描述的更严重。

### 1.2 七个必须马上处理的硬伤

按严重度排序，每条都可复现：

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| 1 | **所有"查看 GitHub Release"链接对公众 404** | `blade-hq/blade-agent` 是 **private** 仓库（`gh repo view` 返回 `isPrivate: true`）；匿名 `curl` 该 release 页返回 404。4 篇 changelog 各有一条这样的链接，`changelog/index.mdx:38` 还有一条"版本信息来自 blade-hq/blade-agent Releases" | 一个公开站点把"权威出处"指向读者打不开的地方，比不给出处更伤信任 |
| 2 | **更新日志自己声明的收录规则没被遵守** | `changelog/index.mdx:38` 写"alpha 实验版本不进入此列表；beta 和正式版会保留"。实际仓库里 2608 线以后共 11 个 beta/正式版 tag，站上只有 4 个。缺失：`v2608.0.0`、`v2608.0.1`、`v2608.0.2`（正式版），`v2608.0.2-beta.1`、`v2608.0.3-beta.1`、`v2608.0.4-beta.1`（beta） | 读者按这句话推断"没写的就是没发过"，会做出错误的升级判断 |
| 3 | **v2610.0.0-beta.1 的升级指引不可执行** | 站上 `v2610-0-0-beta-1.mdx:38` 要求"先部署带模板用户空间改动的 Blade Hub"。原始 release note 明确写着该 blade_hub 分支 `feat/software-factory-template-user-space` **尚未发版**。站上把这句删掉了 | 读者照做会卡在"找不到这个 BH 版本"，且此变更被标注为无兼容窗口的破坏性变更 |
| 4 | **同一版本页漏掉了带安全语义的变更** | `v2610.0.0-beta.0..beta.1` 共 14 个提交，其中 `4204463f6 fix(auth): 管理员判定跟随 BO 表态，首个登录用户不再自动成为管理员 (#1704)` 在站上完全没有出现，站上却收录了"轻量渲染""访问统计"等体感更弱的项 | 权限模型变化是运维必须知道的；漏掉它意味着筛选标准是"听起来像不像卖点"，不是"读者会不会被影响" |
| 5 | **全站只有 2 张截图，并且被跨版本挪用** | `public/images/releases/` 下只有 `v2610.0.0-beta.0/home.png` 和 `software-factory.png`。`v2608-0-3.mdx:16` 用 2610 的截图说明 2608 的变更；blog 文章两张图也是同两张 | 用户要求"比 Notion 更图文并茂"，现状是图文证据近乎为零，且现有的图是错的 |
| 6 | **中文站点以英文身份构建，站内搜索对中文基本失效** | `dist/index.html` 是 `<html lang="en">`；`dist/pagefind/pagefind-entry.json` 只有 `"languages":{"en":...}`，没有 zh 索引；页面上"Search / On this page / Overview / Last updated"全是英文 | 中文没有空格分词，用英文分词器建索引 = 站内搜索对专业读者最常用的查词方式（"沙箱""OAuth 回调""破坏性变更"）命中率极低 |
| 7 | **Blog 首屏的终端截图是编造的** | `blog/index.mdx:21` 的 `terminal-card` 显示 `$ blade agent run`。`blade-agent` 仓库里搜不到这条命令，实际内置 CLI 是 `builtin/clis/` 下的 `blade-cli`、`chrome-cli`、`langchain2cli` | 面向深度技术读者，第一篇文章的主视觉是一条不存在的命令，是最不该犯的一类错误 |

### 1.3 对用户四条判断的正面回应

1. **"把任务交给一个真正能动手的智能体"很 low、标题党** —— 成立，而且问题比"low"更具体：这句话是**竞品贬损式定位**（暗示别家的智能体不能动手），没有信息量，且和副标题 `index.mdx:8`"Blade Agent 不止回答问题"重复表达同一件事两遍。首页确实不需要 Hero。
2. **更新日志应该朴实，左目录右内容** —— 成立。现状是 4 张卡片，其中一张带蓝色渐变的 `featured` 大卡（`custom.css:99`），这是产品发布会的版式，不是变更记录的版式。
3. **Blog 应少而深** —— 方向成立，但现状还没到"少而深"的问题，现在是"只有一篇，而且这一篇没有技术证据"。
4. **三部分不能只是换标题的同一个模板** —— 这条是**字面成立的事实**：`index.mdx`、`changelog/index.mdx`、`blog/index.mdx` 三个文件的 frontmatter 完全同构，都是 `template: splash` + `next: false` + `hero: {title, tagline}`。三个栏目首页在技术上就是同一个模板换了标题。

## 3. 受众与定位

### 3.1 现状：站点在同时假装自己是三种东西

**事实。** 从内容里能读出三种互相打架的自我定位：

- **营销站**：首页 Hero + 四宫格能力卡（`index.mdx:28-33`，WORK / BUILD / CONNECT / OWN 四个英文标签），Blog 首屏的蓝色斜切色块 + 假终端（`custom.css:87-91`），changelog 的渐变 featured 卡。
- **产品手册**：`guide/` 下 11 篇，平均 260～600 汉字，写法是"某功能在哪个端口、有哪几个按钮"。`guide/factory.md` 全文 69 行，句式为"支持多种创建模式""支持任务的汇报与审核流程"。
- **技术出版物**：`api/rest.md` 2234 行、`api/types.md` 446 行、`api/chat-flow.md` 346 行，是真正有信息密度的部分。

**判断。** 这三种定位不是可以共存的层次，而是**互相拆台**。一个架构师从首页的四宫格进来，会预期后面是深度内容；点进 `guide/factory.md` 看到"应用发布：开发完成后，可以将应用直接发布，无需手动部署"（`guide/factory.md:59-61`，全节两句话），就会给整站定性为"市场部做的"。反过来，一个只想接 SDK 的开发者要先穿过一屏 Hero 才能到 `guide/getting-started/`。

最能说明定位混乱的一处细节：**首页 Hero 的第二个按钮"Blade Agent 是什么"指向的是一篇 Blog 文章**（`index.mdx:13-15` → `./blog/introducing-blade-agent/`）。也就是说，"这个产品是什么"这个最基础的文档问题，站点交给了 Blog 回答。Blog 因此被迫承担产品介绍职能，这正是它变成软文的结构性原因。

**改法。** 定下一句可执行的定位，并用它裁剪每一页：

> 这是 Blade Agent 的**技术文档站**。它服务已经决定或正在评估要把 Blade Agent 接进真实工作的人。它不负责说服路人。

推论：
- 说服性内容（为什么智能体重要、和聊天机器人的区别）**全部**归 Blog，而且必须带证据；文档区不写一句。
- 文档区的每一页都要能回答"我照着做能不能跑起来"。答不了的页面要么补齐，要么删。
- 首页不承担转化，只承担**分流 + 状态播报**。

### 3.2 三类读者的实际路径与当前失败点

| 读者 | 他真正想要 | 现在会发生什么 | 判断 |
|---|---|---|---|
| AI 爱好者 | 这东西和 Claude Code / Manus / Dify 比，边界在哪；能不能自己搭 | 首页四宫格 → `guide/getting-started` → "联系销售团队申请试用账号"（`guide/getting-started.md:11`）→ 断掉 | **最严重的漏斗断点**。爱好者拿不到任何可自己动手的入口，站点对他实际上是关闭的 |
| 深度技术人员 | 架构、协议、失败模式、沙箱边界、版本兼容 | 从导航里看不出 `api/` 有 2234 行的 REST 参考；`ops/security.md` 只有 153 汉字且只讲 PyArmor 加壳 | 最有价值的资产（API 参考）在信息架构里被埋在第 4 个折叠分组 |
| 专业人士 / 技术负责人 | 部署形态、升级风险、破坏性变更、数据边界、私有化成本 | changelog 是最相关的栏目，但收录不全、出处 404、升级步骤不可执行 | 站点在他最需要严谨的地方最不严谨 |

**改法。** 首页分流应该按**读者意图**而不是按**栏目名**切分（详见 §6、§7）。

## 4. 逐区审计

### 4.1 首页（`src/content/docs/index.mdx`）

#### 4.1.1 标题与 Hero

**事实。** `index.mdx:6-15`：

```yaml
hero:
  title: 把任务交给一个真正能动手的智能体
  tagline: Blade Agent 不止回答问题。它能读文件、操作浏览器、调用业务技能，也能从一句需求开始搭出可运行的软件。
```

`custom.css:53` 把 h1 放大到 `clamp(3rem, 7vw, 6.2rem)`，`line-height: .98`，截图里这行中文占了三行、约 40% 首屏高度。`custom.css:38-51` 还给 Hero 加了一层斜纹渐变装饰（`.hero::before`）。

**判断。** 逐条说为什么不行：

1. **"真正能动手"是贬低同类，不是描述自己。** 高认知读者读到"真正"两个字的第一反应是"谁不真正"，而不是"哦它能动手"。这类措辞的净效果是降低可信度。
2. **和副标题重复。** 标题说"能动手"，副标题第一句说"不止回答问题"——同一个意思写了两遍，占掉整个首屏。
3. **它是一句愿景，不是一个可核验的陈述。** 相比之下副标题后半句"能读文件、操作浏览器、调用业务技能"是可核验的，反而更有说服力。真正有用的信息被排在了空话后面。
4. **6.2rem 的中文标题在排版上就是错的。** 中文没有词间空格，字重和字面都比拉丁字母满，同样字号的视觉体量大得多。这个尺寸是为英文 display 字体设计的，套到中文上就是截图里那种"标语墙"效果。
5. **首页有 Hero 这件事本身就在给站点定性。** 技术文档站的首页 Hero = 官网落地页。Blade Agent 的官网如果另有其人，这里就是重复；如果没有，那也不该由文档站来兼职。

**改法。** 删掉 `hero` 整个 frontmatter 块，删掉 `template: splash`。首页改成一页普通文档：一行 H1（"Blade Agent 文档"），一段 2～3 句的产品定义（必须包含部署形态和适用边界），然后直接进入分流。字号回到 `--sl-text-3xl` 量级。

如果一定要留一句概括，用可核验的写法，例如：

> Blade Agent 是一个可私有化部署的智能体运行时。它在沙箱里执行命令、驱动浏览器、调用你注册的技能，并通过 REST / Socket.IO 把这些能力开放给你的应用。

这句话里每个名词在文档里都有对应章节，读者可以立刻验证。

#### 4.1.2 三栏目导航条（`index.mdx:18-22`）

**事实。** `.home-rail` 三个格子：使用文档 / 更新日志 / Blog，配 `01 02 03` 序号（`custom.css:62` 用等宽字体染成品牌蓝）。

**判断。** 序号是纯装饰——这三者没有先后顺序，编号暗示了不存在的流程。但**这个区块本身是首页最该保留的东西**，问题只在于它切分的维度错了：按栏目切，读者还得自己把"我要接 SDK"翻译成"这属于使用文档"。而且它和顶部导航（`Header.astro:9-13`）完全重复，同一组三个链接在一屏里出现两次。

**改法。** 保留这个区块的形态（横向分栏、细线分隔），但换成**按意图分流**，并且下钻到二级页面而不是栏目首页。见 §7 线框。

#### 4.1.3 四宫格能力卡（`index.mdx:28-33`）

**事实。** 标题"不是聊天框的另一种皮肤"（`index.mdx:24`），下面四张卡：WORK / BUILD / CONNECT / OWN。`custom.css:66-71` 给每张卡 `min-height: 14rem`、hover 时加蓝色渐变。

**判断。**

1. **英文标签是纯装饰。** 一个全中文站点，四个英文单词既不是术语也不是导航，只是为了让版式看起来像国外 SaaS。
2. **"不是聊天框的另一种皮肤"又是一句贬损式定位**，和 Hero 标题犯同一个错。
3. **四张卡的内容和顶部三栏目导航是同一批信息的第三次重复。** "把能力接进现有产品"= 应用接入，"部署在自己的环境里"= 部署与运维。首页在用三种版式讲同一件事。
4. **卡片里的话没有一句是可核验的。** "长任务会拆分执行，完成后给出结果和产物，而不是只留下一段建议"——读者无法据此判断它能不能干自己的活。
5. `min-height: 14rem` + `h3` 上方 `margin: 2.4rem`（`custom.css:70`）让每张卡有大量空白，四张卡占掉近一屏，承载的信息量约 200 字。**版式规格远高于内容密度**，这是整站最典型的"设计过度"样本。

**改法。** 整块删除。首页不需要能力介绍——需要能力介绍的读者会去看文档区的 overview 页；需要被说服的读者会去看 Blog。如果坚持要在首页说明产品能力，用一段 3～4 句的散文加 2～3 个指向具体文档页的行内链接，占 1/4 屏即可。

#### 4.1.4 版本条（`index.mdx:35-39`）

**事实。** 硬编码了 `v2610.0.0-beta.1` 和它的一句话摘要，带一个绿色呼吸点（`custom.css:79` `.status-dot`，绿色 `#28b86f`）。

**判断。**

1. **必然过期。** 同一个版本号目前存在于 4 个地方：`index.mdx:36`、`changelog/index.mdx:14`、`Sidebar.astro:16`、`changelog/v2610-0-0-beta-1.mdx:2`。发下一个版本要人肉改 4 处，漏一处就是首页在推荐一个旧版本。
2. **绿点是错误信号。** 绿色圆点 + 呼吸光晕在所有运维语境里都表示"运行中 / 健康"。这里它标注的是一个 **beta 预发布**，语义正好相反：这是最不该被绿灯背书的版本类型。
3. **首页只播报预发布是有害的。** 一个刚到站的技术负责人看到首页最显眼的版本是 beta，会误以为这是当前推荐版本。首页应该同时给出"当前正式版"和"最新预发布"两个数字，并且正式版在前。

**改法。** 保留"首页播报版本"这个想法（这是首页少数真正有用的功能），但改成两栏、去掉状态点、并且**从数据源生成而不是手写**（见 §9.1）：

```
当前正式版  v2608.0.4 · 2026-08-12 · 升级说明 →
最新预发布  v2610.0.0-beta.1 · 2026-08-13 · 含破坏性变更 →
```

"含破坏性变更"这类标记应由 changelog frontmatter 的 `breaking: true` 自动带出。

#### 4.1.5 首页其他问题

**事实。** 截图底部有 "Last updated: Aug 13, 2026"。这来自 `astro.config.mjs:31` 的 `lastUpdated: true`，对所有页面生效。

**判断。** 在一个 splash 落地页底部显示"最后更新时间"是无意义的——读者关心的是产品的更新时间，不是这个 MDX 文件被 commit 的时间。而且它是英文。

**改法。** 首页关掉 `lastUpdated`（Starlight 支持 frontmatter 级 `lastUpdated: false`）。文档页保留，但要中文化（见 §5.1）。

**首页最终结论：**

| 元素 | 处置 |

### 4.2 更新日志

#### 4.2.1 列表页（`src/content/docs/changelog/index.mdx`）

**事实。** `template: splash` + hero "更新日志"（同样 6.2rem）+ 4 张 `.release-card`，第一张是 `featured`，`grid-column: span 2`、`min-height: 19rem`、带蓝色渐变背景（`custom.css:99`）。版本号用 `clamp(1.7rem, 3vw, 2.7rem)` 渲染（`custom.css:103`）。

**判断。**

1. **卡片墙是错误的信息形态。** 变更记录的读者行为是"扫描 → 定位到我关心的版本 → 读细节"，卡片墙强制他一屏看 2 个版本、每个版本只给一句话。Notion Changelog 的做法是左侧一列版本目录、右侧长滚动正文，正因为它匹配这个行为。现状与用户诉求正好相反。

4. **没有任何筛选。** 用户明确要"版本筛选"，现状是零。读者无法只看正式版、无法只看有破坏性变更的版本、无法按交付线（2608 / 2610）过滤。当版本数从 4 涨到 40，这个页面直接不可用。
5. **收录规则被违反**（见 §1.2 第 2 条）。`release-source` 那句"beta 和正式版会保留"是站点对读者的承诺，现在是假的。
6. **出处链接对公众 404**（见 §1.2 第 1 条）。

**改法。** 见 §6 和 §7.2：改为左目录 + 右正文的两栏结构，列表页降级为"全部版本"索引表 + 筛选。

#### 4.2.3 正式版 / beta 的表达

**事实。** 两种徽章：`.release-badge.beta`（`#ffd891` 橙底）和 `.release-badge.stable`（`#a9ecc9` 绿底），文案分别是 `BETA` 和 `正式版`。侧栏（`Sidebar.astro:16-20`）用同样两个词。

**判断。**

1. **中英混用没有理由。** 一个写 `BETA`，一个写 `正式版`。要么都中文（"预发布 / 正式版"），要么都英文。
2. **徽章只回答"是不是 beta"，没回答读者真正的问题：我能不能升。** 需要的维度是：是否含破坏性变更、是否需要同步升级其他组件（BH / SDK / 镜像）、是否有已知阻塞问题。现在这些信息散在正文里，扫描不到。
3. **软糖色（`#ffd891` / `#a9ecc9`）在深色主题下的对比度可疑**（`custom.css:107-108` 只定义了浅色值，没有 dark 变体）。深色背景配浅黄浅绿底、深色文字，实际是浅色小块糊在深色页面上。
4. **alpha 被完全排除是对的判断，但要写清楚为什么。** 现在的措辞"alpha 实验版本不进入此列表"没说明 alpha 是什么（内部验证？功能预览？），读者看到仓库里有 `v2610.0.1-alpha.1` 会困惑。

**改法。** 把徽章从"版本类型"升级为**风险标记组**，最多 3 个，全中文：

```
[正式版]  [破坏性变更]  [需同步升级 Blade Hub]
[预发布]  [仅测试环境]
```

由 frontmatter 字段驱动（见 §8.1），列表页可按这些标记筛选。

#### 4.2.4 图文证据

**事实。** 全站截图资产：`public/images/releases/v2610.0.0-beta.0/{home.png, software-factory.png}`，共 2 张，被 5 处引用（3 处 changelog + 2 处 blog），其中 2 处是跨版本挪用。

**判断。** 用户要"比 Notion Changelog 更图文并茂"。现状连"有图"都算不上——是**同两张图在五个地方轮转**。而且 `software-factory.png` 同时被用来说明 v2608.0.3 的"智能应用开发"、v2610.0.0-beta.1 的"模板用户体系"和 blog 的"软件工厂"，三个完全不同的论点。这已经不是配图不足，是**配图在误导**。

**改法。**

- 建立强制规则：**没有本版本截取的证据，就不放图**（宁可无图，不可挪用）。
- 目录规范：`public/images/releases/<完整tag>/<语义化文件名>.png`，禁止跨目录引用。CI 加一条校验：changelog 页面引用的图片路径必须以自身 tag 开头。
- 每个版本的图文预算：**1～3 张**。选图标准是"这张图能证明正文里的某个具体断言"，不是"这个功能好看"。
- 除截图外，更适合技术读者的证据形式：变更前后的配置片段 diff、接口请求/响应对照、终端输出、错误信息原文。这些比 UI 截图更耐读且不会因为改版而失效。

#### 4.2.5 升级 / 兼容信息

**事实。** 4 篇的升级信息形态各异：beta.1 用有序列表 3 步 + 一个 `:::caution`；beta.0 用无序列表 3 条"部署提示"；0.4 用一段散文；0.3 用一段散文。

**判断。** 结构不一致 = 无法扫描。运维读者的诉求是"在同一个位置、用同一种格式，看到升级前提 / 步骤 / 回滚方式"。现在他必须每篇通读。

**改法。** 强制模板（见 §8.1），每篇末尾固定四块：**前置条件 → 升级步骤 → 回滚方式 → 已知限制**。没有内容就写"无"，不允许省略——"无"本身是信息。

#### 4.2.6 commit / PR 链接

**事实。** 目标仓库私有，所有 release/commit/PR 链接对公众 404。

**判断。** 用户想要 commit/PR 链接的诉求是对的（可追溯性是技术出版物的基本要求），但**在私有仓库前提下，直接贴链接是净负面**：它给了读者一个假的可验证承诺。

**改法。** 三选一，按可行性排序：

1. **展示不可点的引用**（推荐，零成本）：正文写 `#1716`、`c1c754b`，用等宽样式，不加超链接；页面顶部一句"提交编号对应 blade-hq/blade-agent 内部仓库，供支持工单引用"。既保留可追溯性，又不撒谎。
2. **建一个公开的镜像 changelog 仓库**，只同步 release note，链接指向它。
3. **接入工单系统**：把 `#1716` 链到内部 issue 跟踪的公开视图（如果有）。

无论哪种，`changelog/index.mdx:38` 那句"版本信息来自 blade-hq/blade-agent Releases"的超链接必须去掉。

| `:47-49` "我们接下来要解决的事" | ✅ 承认"'能做'离'每次都做对'仍有距离"是加分项，是全文第二诚实的地方 |
| `:51` "不妨别问它'你能做什么'。给它一份真实材料和一个拖了几天的任务。" | ⚠️ 写法漂亮，但它是 **CTA**。技术文章不需要以号召结尾 |

**总体判断。** 这篇文章的骨架是对的（问题 → 缺口 → 我们的做法 → 局限），**但每一节都在该给证据的地方给了形容词**。它读起来像"一篇写得比较克制的产品介绍"，不像"一个工程团队在讲他们踩过的坑"。核心缺陷用一句话概括：**通篇没有一个数字、一段代码、一条日志、一个具体失败案例的复盘。**

另外两处需要注意的措辞：`:13` "从这个不太体面的缺口出发"——"不太体面"是拟人化的修辞，用在描述技术缺口上略显做作；`:29` "这比收藏一段 prompt 麻烦，但也更诚实"——"诚实"这个词用在技术方案上是同类问题。这类修辞单独看不致命，密集出现就会让读者感到"这是被润色过的文案"。

#### 4.3.3 选题标准与文章密度

**判断 + 改法。** Blog 的发布门槛应该是一个**可否决的清单**，不满足就不发（详见 §9.2）。核心是三条：

1. **必须有一手证据。** 代码 / 配置 / 日志 / 数据 / 时间线，至少一样。没有证据的观点文一律不发。
2. **必须有一个别人不同意也无所谓的观点。** 如果全文的结论是"我们的产品很有用"，那它是市场材料，不是 Blog。
3. **必须有人署名。** 作者对文中的技术判断负责。

**密度建议：** 每月 1 篇，宁缺毋滥。判断依据：Linear 的 Blog 更新频率就在这个量级，而且他们从不为了保持节奏发凑数的文章。对一个刚起步的技术 Blog，**连续三篇有分量的文章比十二篇平庸的更能建立信任**。

**选题池（从现有材料里能立刻立项的四个）：**

| 选题 | 现成素材 | 为什么值得写 |
|---|---|---|
| 浏览器操作后如何确认"真的成功了" | `chrome-cli` 的 `--confirm` 设计、`#1696` 历史导航不依赖导航事件、`#1700` 手动模式避让 | 这是智能体做 Web 自动化的真问题，有真实代码支撑 |
| 一次没有兼容窗口的破坏性变更是怎么发生的 | `#1716` 模板 id 从单段改两段、BA/BH 双向失败矩阵、BH 分支未发版 | 讲一次自己的协同失误，可信度最高的题材 |
| 长任务的成果为什么会"消失"，以及产物卡片的设计 | `#1697` 会话结束成果汇总优化、会话小结带产物 | 有明确的问题定义和改动记录 |
| 把三个 CLI 收进 `builtin/clis/` 前后 | `#1689` | 讲沙箱内工具的边界与命名，适合深度读者 |

注意：这四个选题都来自 changelog。**这说明 changelog 做扎实之后，Blog 的选题会自动产生**——这也是 §9 治理流程的设计前提。

### 4.4 使用文档

#### 4.4.1 深浅极度不均

**事实。** 49 个 md 文件，行数分布：

- 最短：`ops/security.md` 25 行（153 汉字）、`ops/monitoring.md` 33 行、`ops/oauth.md` 37 行、`guide/getting-started.md` 38 行（260 汉字）
- 最长：`api/rest.md` 2234 行、`api/types.md` 446 行、`api/chat-flow.md` 346 行
- `guide/` 11 篇合计约 600 行，`api/` 6 篇合计约 3700 行

**判断。** 这不是"有的详有的略"，是**两个不同项目拼在一起**：`api/` 是从代码或 OpenAPI 生成的严肃参考，`guide/` 是手写的功能巡览。中间缺的那一层——概念解释、真实场景端到端示例、架构决策说明——整站都没有。专业读者恰恰住在这一层。

#### 4.4.2 具体缺陷

**a) 快速开始在第一步就把读者赶走**

**事实。** `guide/getting-started.md:9-11`：

```
### 公网演示环境
联系销售团队申请试用账号。
```

**判断。** 全文 260 汉字，第一个动作是"联系销售"。对 AI 爱好者和自己做技术选型的开发者，这一句就是终点。而且"销售团队"没有联系方式——连这一步都不可执行。

**改法。** 快速开始必须给一条**读者今天就能自己走完的路径**。既然文档里已经有 `ops/docker.md`（158 行），把 Docker 单机起一套的最小路径提到快速开始，明确写出：需要多少内存 / 需要什么模型服务 / 大约几分钟 / 起来之后先做哪个验证动作。"联系销售"作为并列选项之一，不作为唯一选项。

**b) 概念内容重复**

**事实。** `guide/solutions-and-roles.md:13-14` 和 `agent-dev/concepts.md:15-16` 用几乎相同的句子解释同一组例子：

- guide：「软件工程」解决方案：包含需求分析、UI 设计、任务拆分等角色…「智能招投标」解决方案：包含标书分析、合规检查等角色，每个角色只使用招投标相关技能，确保输出专业、准确。
- agent-dev：**智能招投标** -- 包含标书分析、合规检查等角色，每个角色只使用招投标相关技能，确保输出专业、准确。

后半句一字不差。

**判断。** 两处会独立漂移，早晚互相矛盾；搜索时两条结果争夺同一查询。

**改法。** 概念只写一处（放 `agent-dev/concepts`），`guide/solutions-and-roles` 改为纯操作（怎么切换、切换时发生什么、什么时候该切），概念部分用一句话 + 链接。

**c) 两组同名页面**

**事实。** `agent-dev/concepts.md` 和 `integration/concepts.md` 都叫「核心概念」；`agent-dev/debugging.md` 和 `integration/debugging.md` 都叫「调试与排查」。

**判断。** 侧栏里能靠分组区分，但搜索结果、浏览器标签、外部分享出去的链接全都无法区分。

**改法。** 改成自解释标题：「智能体开发核心概念」/「接入核心概念」，「技能与解决方案调试」/「SDK 接入排障」。

**d) 版本示例已过期，且与 changelog 互相矛盾**

**事实。**

- `integration/concepts.md:14`："例如后端是 `v1.0.10`，前端 SDK 就装 `@blade-hq/agent-kit@1.0.10`"
- `integration/frontend/react.md:16` / `vue.md:18`：注释"如 1.0.10"
- 当前实际版本号是 `2608.0.4` / `2610.0.0-beta.1`，`v1.2.1-beta.17` 之后已切换到日期式版本线
- 获取版本的方式也有两种说法：`integration/concepts.md:10` 说"后端版本号在 Web UI 左上角 logo 旁查看"，`changelog/v2608-0-3.mdx:33` 说"按 `GET /api/version` 返回值固定 SDK 版本"
- **`GET /api/version` 在 `api/` 全部 6 篇里都不存在**

**判断。** 三重问题叠加：例子过期（读者会以为版本号长 `1.0.x` 那样）、同一件事两种做法、推荐的那种做法没有文档。

**改法。** 统一到 `GET /api/version`，在 `api/rest.md` 补上这个端点（请求 / 响应 / 示例），所有示例版本号改成当前正式版，并在 §9.3 加一条发布前校验。

**e) 用 ASCII 画界面，真截图却给了 Blog**

**事实。** `guide/factory.md:42-57` 用 ASCII 框线画了软件工厂的三栏界面；`guide/solutions-and-roles.md:20-31`、`agent-dev/debugging.md:17-33` 同理。而真实的 `software-factory.png` 躺在 `public/images/releases/` 下，被 blog 和 changelog 用了。

**判断。** 用途搞反了。ASCII 图适合表达**结构和数据流**（`integration/concepts.md:82-109` 的时序图就是好例子，比截图更清楚），不适合表达**界面长什么样**——后者截图一张顶一切，而且 ASCII 界面图在不同字体下会错位（`guide/factory.md:43` 的中文表格框线在非等宽渲染下已经对不齐）。

**改法。** 界面 → 截图；协议、时序、目录结构 → 保留 ASCII / Mermaid。`guide/factory.md` 的三栏图换成真截图。

**f) 运维章节对专业读者太浅**

**事实。** `ops/security.md` 全文只讲两件事：PyArmor 加壳、OAuth 公钥校验。`ops/monitoring.md` 只讲 Prometheus / Grafana 端口和三个仪表盘名。

**判断。** 技术负责人评估私有化部署时的问题清单是：沙箱怎么隔离、逃逸边界在哪、会话工作区的数据留在哪 / 保留多久 / 怎么删、模型调用会不会带业务数据出网、API Key 的权限范围和吊销机制、多用户之间的记忆是否可见（这一条 changelog 里提到"共享记忆默认对他人关闭"，但 `ops/security.md` 只字未提）、审计日志。**这些一条都没有。** 现有的"PyArmor 加密防止源码泄露"回答的是厂商自己的关切，不是客户的关切。

**改法。** `ops/security.md` 重写为面向部署方的安全说明，至少覆盖：数据边界（工作区 / 记忆 / 上传文件的存储位置与生命周期）、身份与权限（API Key 范围、吊销、管理员判定 —— 注意 `#1704` 刚改过）、网络出向（哪些请求会离开内网）、沙箱隔离模型、审计能力。PyArmor 那节降级为一小节或移到别处。

**g) frontmatter 缺 description**

**事实。** 49 个 `.md` 里 43 个没有 `description:` 字段，只有 6 个有。

**判断。** Starlight 用它生成 `<meta name="description">` 和社交卡片；pagefind 的结果摘要也会受影响。43 个页面被分享出去时没有摘要。

**改法。** 补齐，并在 CI 加校验（见 §9.3）。

#### 4.4.3 使用文档缺失的内容（专业读者会问但站上答不了）

| 缺口 | 判断 |
|---|---|
| **架构总览** | 没有一页解释 Blade Agent / Blade OS / Blade Hub / Blade OAuth / LLM Gateway / Gitea / 沙箱 之间的关系。这些名字散落在 `guide/` 和 `ops/` 各处，读者必须自己拼图。这是**最该补的一页** |

### 4.5 视觉与阅读

**事实清单（`src/styles/custom.css`）：**

| 位置 | 内容 |
|---|---|
| `:1` | 从 Google Fonts 加载三套字体：Manrope（8 个字重）、IBM Plex Mono（3 个）、Noto Serif SC（3 个） |
| `:11-12` | `--sl-content-width: 62rem`、`--sl-text-5xl: 3.8rem` |
| `:25` | `body { letter-spacing: -0.008em }` 全局负字距 |
| `:27-29` | 标题 `letter-spacing: -0.035em` |
| `:31` | 正文 `line-height: 1.82` |
| `:53` | hero h1 `letter-spacing: -.065em` |
| `:84`, `:112` | Blog 标题和 deck 用 `Noto Serif SC` 衬线 |
| `:87-91` | Blog 视觉块：`clip-path` 斜切 + `rotate(-2deg)` 终端卡 + `1.1rem` 硬投影 |
| `:115-119` | `.card-grid` / `.docs-card` 样式 |

**判断。**

1. **负字距用在中文上是错的。** `letter-spacing` 对中文的作用是压缩汉字间距（不是像拉丁字母那样收紧字形间的空隙）。`-0.008em` 全局、标题 `-0.035em`、Hero `-0.065em`——Hero 那个数值在中文下会让相邻汉字明显粘连，截图里"把任务交给一个"几个字已经能看出挤压。**这是照搬英文 display 排版规则的直接后果。**
2. **`Noto Serif SC` 只用在 Blog** 是有意为之的分区，方向可以理解（编辑内容 vs 参考内容），但配合 3.5rem 的字号和衬线体，观感更接近杂志封面而非工程博客。判断：**保留衬线用于正文引导段，但标题字号砍到 2rem 以内**。
3. **Google Fonts 在中国大陆访问不稳定。** `Noto Serif SC` 全字重是巨大的 CJK 字体文件。首屏依赖外部 CDN 加载中文衬线体，实际效果很可能是长时间无字体或回退。**判断：这是性能与可用性问题，不只是审美问题。**
4. **`.card-grid` / `.docs-card` 是死代码**——`grep` 全站内容文件，零引用。5 行 CSS 无人使用。
5. **`line-height: 1.82` + `62rem` 内容宽度**：行高对中文合适，但 62rem 对中文正文偏宽（中文在同样宽度下每行字数远多于英文）。文档页正文建议收到 48～52rem，参考页（含宽表格）保持 62rem。
6. **hover 动效过多**：`.release-card` / `.docs-card` / `.home-rail a` 都有 `translateY(-2px)` 位移（`custom.css:132`），`.capability-grid article:hover` 有渐变。文档站的卡片浮起动画属于典型的"官网手势"。
7. **深色主题下的徽章色未定义**（`custom.css:107-108` 只有一组值），需要检查对比度。

**专业技术读者真正需要的阅读体验：**

- 稳定可预测的版式：同类页面长得一样，扫描成本低
- 代码块要好用：可复制、有语言标注、长行处理得当、行号可选
- 正文宽度适中，中文正文 40～50 字/行
- 表格能横向滚动而不撑破布局
- 站内搜索能命中中文术语（当前失效，见 §5.1）
- 明确的"最后更新"和"适用版本"标注
- 无干扰：没有浮起动画、没有渐变卡、没有装饰性斜纹

**改法优先级：** 去掉全局负字距（或把中文字距设为 0）→ 字体自托管或改用系统字体栈 → 砍掉装饰性动效和斜切块 → 删死 CSS → 分级内容宽度。

## 5. 跨站问题

### 5.1 站点以英文身份构建（P0）

**事实。**

- `astro.config.mjs` 没有配置 `locales` / `defaultLocale`，Starlight 默认 `lang="en"`
- `dist/index.html`、`dist/blog/introducing-blade-agent/index.html` 均为 `<html lang="en" dir="ltr">`
- `dist/pagefind/pagefind-entry.json`：`{"languages":{"en":{...,"page_count":57}}}` —— 57 个页面全部用英文分词器索引
- 界面文案全英文：`Search`、`On this page`、`Overview`、`Last updated: Aug 13, 2026`、主题切换的 `Auto`

**判断。** 三重后果：

1. **站内搜索对中文基本失效。** 英文分词器按空白/标点切词，一整句中文会被当成一个或几个巨型 token。读者搜"破坏性变更""沙箱镜像""OAuth 回调"命中率极低。**对一个 57 页的技术站，搜索失效等于内容失效。**
2. **屏幕阅读器会用英文发音读中文内容**（`lang="en"`），无障碍问题。
3. **搜索引擎的语言判定和中文站点观感受损。**

**改法。** `astro.config.mjs` 里补 `locales: { root: { label: '简体中文', lang: 'zh-CN' } }`。Pagefind 会据此生成中文索引，Starlight UI 文案自动中文化。这是**一处配置改动，收益覆盖全站**——性价比最高的一条。改完必须复验 `pagefind-entry.json` 里出现 `zh` 索引。

同时可以去掉 `Header.astro:2,29` 的 `LanguageSelect`——单语言站点不需要语言切换器。

### 5.2 内容与代码耦合，无法规模化（P0）

**事实。** 新增一篇 Blog 或一个版本，需要人肉改动的位置：

| 动作 | 需要改的文件 |
|---|---|
| 发一个新版本 | ① `changelog/vXXX.mdx`（新建）② `changelog/index.mdx`（加卡片）③ `Sidebar.astro:15-21`（加侧栏条目）④ `index.mdx:35-39`（首页版本条） |
| 发一篇新文章 | ① `blog/xxx.mdx`（新建）② `blog/index.mdx`（头条卡 + 日期 + 阅读时长）③ `Sidebar.astro:11-14`（加侧栏条目） |

**判断。** **侧栏列表写死在 `.astro` 组件里**是最严重的一处——内容作者必须改前端代码才能发内容。这解释了为什么会出现 §1.2 第 2 条的版本缺口：加一个版本要动 4 个地方，漏掉是必然的，不是偶然的。

**改法。** 建立两个内容集合，由数据驱动一切列表：

```ts
// src/content.config.ts
changelog: defineCollection({ schema: { version, date, channel, breaking, requires, summary, ... } })
blog:      defineCollection({ schema: { title, date, author, tags, summary, ... } })
```

然后：
- `Sidebar.astro` 改为 `getCollection('changelog')` / `getCollection('blog')` 排序渲染
- `changelog/index.mdx`、`blog/index.mdx` 的列表从集合生成
- 首页版本条取 `channel === 'stable'` 和 `channel === 'beta'` 各一条最新
- 阅读时长由正文字数计算（中文按 400 字/分），不再手写

**判断：这是所有改造的地基。** 不做这一步，后面所有内容规范都会在下一次发版时失效。

### 5.3 事实校验缺失（P0）

**事实。** §4.2.2 列出的 11 处事实性问题，全部可以通过对照 `git log <上一tag>..<本tag>` 和 `gh release view` 发现，但没有任何流程做这件事。

**改法。** 见 §9.1 和 §9.3。

### 5.4 三个栏目共用同一个 splash 模板（P1）

**事实。** `index.mdx`、`changelog/index.mdx`、`blog/index.mdx` 的 frontmatter 结构完全相同（`template: splash` + `next: false` + `hero`）。

**判断。** 这就是用户第 4 条意见的技术根源。三个栏目职责不同，就不该长得一样：首页是分流器，changelog 是可筛选的记录索引，blog 是文章列表。

**改法。** 三者各自使用不同布局（见 §7）。

### 5.5 品牌与命名不一致（P2）

**事实。** `README.md:1` 写"Blade OS 帮助文档"；站点 title 是"Blade Agent"；`astro.config.mjs:7` 的 description 是"Blade Agent 使用文档、更新日志与产品 Blog"；`dist/index.html` 的 `<title>` 是 `Blade Agent | Blade Agent`（重复）。

**改法。** 统一为"Blade Agent 文档"；首页 frontmatter 加 `title` 覆盖以消除重复的 `<title>`；README 改名并补充内容治理说明（见 §9）。

### 5.6 缺 RSS / 订阅（P2）

**事实。** 无 feed。

**判断。** changelog 的 RSS 对运维读者价值最高——他们希望版本一发布就知道，而不是定期回访网页。

**改法。** 用 `@astrojs/rss` 出两个 feed：`/changelog/rss.xml`、`/blog/rss.xml`，在对应页面页脚给出订阅链接。

## 6. 推荐信息架构

### 6.1 三个栏目各自的任务

| 栏目 | 一句话任务 | 成功标准 | 明确不做 |
|---|---|---|---|
| **使用文档** | 让人把 Blade Agent 装起来、用起来、接进自己的系统 | 读者能自己走完一条端到端路径而不需要问人 | 不做产品说服、不做版本叙事 |
| **更新日志** | 让人判断"我该不该升、升了会坏什么、坏了怎么退" | 运维不看 GitHub 就能做升级决策 | 不做功能营销、不做 featured 头条 |
| **Blog** | 说清楚我们为什么这样设计，包括做错的部分 | 一个不用 Blade Agent 的工程师读完也有收获 | 不做功能公告（那是 changelog 的活）、不做入门教程（那是文档的活） |

**边界规则（用来裁决内容该放哪）：**

- 描述「怎么做」→ 文档
- 描述「变了什么」→ 更新日志
- 描述「为什么这样做 / 我们踩了什么坑」→ Blog
- 一篇内容同时属于两类 → 拆开，互相链接，不要复制

### 6.2 顶层结构


### 9.1 从 blade-agent 主分支生成高质量 changelog

目标：**让"覆盖完整"成为流程保证，而不是作者的自觉**。

```
① 触发：blade-agent 打出 beta/正式版 tag
   ↓
② 生成事实底稿（脚本，不经模型）
   git log <上一同类型tag>..<本tag> --format="%h|%s"
   gh release view <tag> --json body
   → 产出 draft.md：提交清单 + 原始 release note + 提交数
   ↓
③ 分类（人 + 模型协作，逐条不得漏）
   每个提交打三个标签：
   - 子系统（软件工厂 / 浏览器 / 会话 / SDK / 身份权限 / 沙箱 / …）
   - 受众影响（用户可见 / 运维必须知道 / 仅内部）
   - 风险（破坏性 / 需同步升级 / 配置变更 / 无）
   规则：任何带「身份权限」「数据可见性」「网络出向」标签的提交，
        自动升级为「运维必须知道」，禁止折叠
   ↓
④ 写作（套 §8.1 模板）
   「仅内部」的提交进折叠区，其余全部进主区
   ↓
⑤ 校验（CI，见 §9.3）
   - range 内提交数 == 主区条数 + 折叠区条数    ← 防漏
   - breaking=true 时必须有「部署前必读」小节
   - 图片路径以本 tag 开头
   - 四块固定小节齐全
   ↓
⑥ 复核（发布前，另一个人）
   只问一个问题：一个运维读完这一页，能不能独立决定升不升？
```

**补齐历史缺口（P0）：** 按此流程补 `v2608.0.0` / `0.1` / `0.2` 三个正式版。三个 beta（`v2608.0.2-beta.1` / `0.3-beta.1` / `0.4-beta.1`）建议**改规则而不是补页面**——它们是同代码的验证版，写进对应正式版页面的"验证历史"一行即可。相应地，`changelog/index.mdx` 的收录声明改成：

> 收录 blade-agent 主分支的正式版与独立预发布版本。用于验证同一份代码的 `-beta.N` tag 不单独建页，记在对应正式版页面内。alpha 为内部实验版本，不收录。

**判断：** 规则改成"能做到的样子"，比补一堆没内容的页面更诚实。但**规则一旦写出来就必须是真的**——现在的问题不是规则太严，是规则和事实不符。

### 9.2 Blog 发布门槛

一篇文章要发布，必须逐条打勾，**任何一条不过就不发**：

| # | 门槛 | 判断依据 |
|---|---|---|
| 1 | 有一个具体的技术问题，能用一句话说清 | 说不清 = 还没想清楚 |
| 2 | 有一手证据（代码 / 配置 / 日志 / 数据 / 时间线） | 只有观点 = 软文 |
| 3 | 有署名作者，且作者对文中判断负责 | 无署名 = 无人负责 |
| 4 | 有一个别人可能不同意的观点 | 没有 = 市场材料 |
| 5 | 至少写了一处"我们试过但没用"或"还没解决" | 只有成功 = 不可信 |
| 6 | 所有命令 / 路径 / 接口 / 版本号已在代码库核实 | 见 §9.3 |
| 7 | 不与文档区重复（教程归文档，公告归 changelog） | 重复 = 放错地方 |
| 8 | 全文没有一句话可以删掉而不损失信息 | 删得掉 = 是填充 |

**节奏：** 每月不超过 1 篇，可以连续几个月不发。不为节奏凑数。

**AI 味自查清单**（写完扫一遍，命中即改）：

- "没有魔法""不是银弹""并非万能" —— 无信息的转折模板
- "值得注意的是""换句话说""总而言之" —— 填充连接词
- 三项并列排比连续出现 3 次以上 —— 模型的默认节奏
- 每段都是「陈述 + 转折 + 升华」的三句结构
- 用形容词代替数字（"显著提升""大幅减少"）
- 结尾是号召或展望

### 9.3 事实校验规则（CI + 人工）

**可自动化的（进 CI，失败即阻断合并）：**

| 检查 | 实现 |
|---|---|
| 内链有效 | 已有 `starlight-links-validator`，保留 |
| 外链有效且非 404 | 新增。**必须覆盖 GitHub 链接**——这条能直接抓出 §1.2 第 1 条 |
| 每个 md/mdx 有 `description` | 新增。当前 43 个文件会失败 |
| changelog 提交数守恒 | 新增。见 §9.1 ⑤ |
| changelog 图片路径以本 tag 开头 | 新增。当前 `v2608-0-3.mdx` 会失败 |
| 站点构建后 `lang` 为 `zh-CN`、pagefind 含 zh 索引 | 新增。当前会失败 |
| 文中出现的 `/api/...` 路径在 `api/rest.md` 中存在 | 新增。当前 `GET /api/version` 会失败 |
| 版本号格式合法且 tag 真实存在 | 新增，比对 tag 列表 |
| 阅读时长、日期不得手写 | 由集合生成，从模板层面杜绝 |

**只能人工的（发布前 checklist）：**

1. **命令与路径核实**：文中每条命令在代码库 `grep` 一次。`$ blade agent run` 就是漏了这一步。
2. **截图归属核实**：这张图是本版本截的吗？UI 和当前版本一致吗？含不含真实用户数据？
3. **升级步骤可执行性**：照着这三步，今天能不能做完？依赖的组件发版了吗？
4. **权限/数据类变更是否遗漏**：对照提交清单，专门扫一遍身份、鉴权、可见性相关的改动。

**截图规则：**

- 路径：`public/images/releases/<完整tag>/<语义名>.png`
- 禁止跨版本引用
- 必须清除真实用户名、邮箱、token、内网地址
- 每张图必须有说明具体内容的 `alt`（现有的 `alt="Blade Agent 对话首页"` 合格，`alt="软件工厂项目创建页面"` 描述的却不是本版本的内容 —— 图错了 alt 就跟着错）
- 界面改版后，引用旧图的页面要么换图，要么加"截图基于 vX.Y" 标注
