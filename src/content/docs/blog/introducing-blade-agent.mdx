<p class="article-deck">网页自动化里最危险的假成功，是点击命令正常退出，但业务状态根本没变。我们宁可多花几秒核对，也不让智能体在错误前提上继续往下做。</p>

## 问题不在点击本身

一个按钮被 Playwright 点到，只能证明事件发出去了。它不能证明登录没有过期，也不能证明后端接受了请求；页面可能把结果开到新标签，单页应用可能只改 URL，表单可能原地弹出面板。还有一种更麻烦：网络慢，命令超时，但第一次点击其实已经生效。自动重试会把付款、提交或删除做两遍。

早期实现只看当前页面 URL。遇到 `target="_blank"`、不改地址的弹层和异步表单时，它经常把成功判成失败；如果让模型重试，副作用就不可控。

## 现在按证据强弱逐层判断

`builtin/clis/chrome-cli/chrome` 里的 `check_outcome()` 会在 `click`、`press` 和 `fill` 后检查五类证据，找到明确结果就停止：

```text
1. 是否出现新标签；只有一个时，把它归到当前会话并切过去
2. 当前标签 URL 是否变化
3. 表单值是否变化（press）
4. DOM 内容指纹是否变化
5. 仍无法判断时，保存操作前后截图，交给后续步骤比较
```

这套顺序不是为了追求“智能”。前四层都是确定性判断，只有前四层都没给出答案时，才把截图交给模型。代码注释里写得很直白：新标签和 URL 比页面视觉更明确，先用便宜且可复查的证据。

实际命令也保持简单：

```bash
chrome click '#submit'
chrome url
chrome text 'body'
```

如果点击触发 JavaScript 确认框，默认动作是取消。只有用户明确同意后，调用方才加 `--confirm` 重试：

```bash
chrome click '#delete' --confirm
```

## 我们试过但没用的做法

固定等待最省事，比如点击后 `sleep 2`。它在演示环境里看着正常，一到慢网络就误判；把等待改成十秒，只是让每一步都变慢，仍无法回答“页面到底改了什么”。

只等 `networkidle` 也不够。很多后台页面常驻 WebSocket 或轮询，请求永远不会归零；反过来，纯前端状态变化可能没有任何网络请求。只看 URL 同样漏掉弹层、选中状态和原地更新。

我们最后保留了网络空闲等待，但它只负责给页面一点稳定时间，不负责判定业务成功。成功要靠可见状态变化证明。

## 仍然没解决的部分

DOM 指纹变化只能证明页面变了，不能证明变化符合业务目标。广告轮播、未读数刷新也会改变 DOM。前后截图可以补一些信息，但它依赖模型判断，结果不如 URL、字段值和明确文本稳定。

因此，Skill 作者仍要写验证条件。提交审批后检查状态文字，上传文件后检查文件名，发布应用后请求健康端点。Chrome CLI 提供的是一层通用防线，不是业务验收器。

另一个边界是副作用：当命令超时且状态不明时，CLI 不应悄悄重放 `click` 或 `press`。现在的实现会把不确定状态报出来，让上层决定是检查页面、询问用户，还是停止任务。这个停顿有时烦人，但比重复提交更便宜。
