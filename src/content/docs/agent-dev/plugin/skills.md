## 什么时候需要 Skill

一个输入明确、结果简单的查询工具，可以先只提供 MCP。若查询涉及业务口径、多个操作的先后顺序或结果解读，应加入 Skill：工具负责执行，Skill 说明在什么情况下执行、如何组合结果以及不能作出哪些推断。

例如，销售金额与库存数量虽然都有数字，但不能合并求和；演示数据也不能当成实时业务记录。把这些规则写进 Skill，比在每次对话中重新解释更合适。

## 编写 `SKILL.md`

在快速开始的包中增加 `skills/query/SKILL.md`：

```markdown
---
name: business-data-query
description: 当用户要查询业务数据插件中的销售或库存演示数据、汇总金额或库存数量时使用。
---

# 业务数据查询

## 执行步骤

1. 确认用户要查销售还是库存；不明确时先询问。
2. 使用本会话业务数据插件的 query_dataset 工具，销售传 sales，库存传 inventory。
3. 根据实际返回的 rows 计算结果，注明这是演示数据。
4. 销售按 amount 汇总，库存按 quantity 汇总，不混合不同单位。

## 结果与失败处理

- 展示所查数据集、记录数和汇总结果；空结果明确说明没有匹配记录。
- 工具失败时说明尚未取得数据，不根据示例或历史回答编造本次结果。
- 用户要求实时数据时，说明本插件当前只提供固定演示数据。
- 需要账号配置时，引导用户打开插件配置，不在聊天中索要密码或令牌。
```

触发描述应写具体的用户意图，避免“任何问题都使用本技能”。正文中引用原始 MCP 工具名即可，BA 会提供实际可调用入口，不要复制某个会话生成的绝对路径或工具别名。

包内技能使用插件名称隔离，BA 会把内容投影到会话技能目录。取消激活或配置未就绪时，不会把这些技能作为已就绪的插件能力呈现。

## 组织多个技能与辅助文件

按业务任务拆分技能，例如 `query` 负责查询、`report` 负责整理报告，而不是为每个工具都创建一份 Skill。BA 自动发现的是 `skills/<目录>/SKILL.md`，目录名称建议采用小写字母、数字和连字符。

```text
skills/
├── query/
│   ├── SKILL.md
│   └── references/
│       └── metrics.md
└── report/
    ├── SKILL.md
    └── templates/
        └── report.md
```

在技能正文中说明何时读取相对路径下的资料，例如“汇总前读取 `references/metrics.md` 核对指标单位”。技能会投影到独立位置，所以不要假定 `../../server.py` 仍能找到插件根目录文件；执行插件业务代码通过 MCP 工具，技能自己的辅助资源随技能目录交付。

重新打包时显式加入 `skills`：

```bash
zip -r ../business-data-with-skill.zip plugin.json mcp.json requirements.txt server.py skills
```

## 验证技能触发与组合效果

分别验证以下场景，并查看实际读取的技能和调用的工具：

| 用户输入或操作 | 预期行为 |
| --- | --- |
| “汇总销售金额” | 查询 `sales`，根据返回数据求和并标明演示数据 |
| “帮我写封请假邮件” | 不调用业务数据插件 |
| “查一下数据” | 先澄清数据集，不任意选择业务口径 |
| 同时激活报告插件 | 数据查询与报告生成各自完成对应任务，不重复查询或争夺全部任务 |
| 取消激活业务数据插件后开启下一轮 | 不再把它作为当前可用的插件能力 |

Skill 是给智能体的业务指引，权限校验仍要写在工具或业务系统里。提示词中的“只读”不能代替服务端对写操作的限制。
